# Requirements Document

## Introduction

The device invite/join flow allows ZVault users to pair devices easily without manually copying 64-character hex public keys. The current implementation requires users to somehow know and paste the other device's Nostr public key — but there is no mechanism to retrieve or share that key.

This spec redesigns the device pairing UX with two complementary flows:

1. **Invite flow (A invites B):** Device A generates a shareable invite (link, QR code, or text code) containing its own public key + vault identity info. Device B imports this invite, generates its own identity, and sends back a join response. Device A confirms and admits B.

2. **Join-request flow (B requests to join A):** Device B generates a join request (link, QR code, or text code) containing its public key. Device B gives this to Device A (an existing member). Device A scans/pastes the request and admits B.

Both flows eliminate the need to manually locate, copy, and paste raw public keys.

## Glossary

- **Invite Code**: A compact, shareable token generated by an existing device (the inviter). Contains the inviter's public key, vault ID, and an optional label. Can be rendered as a QR code, a URL, or a copyable text string.
- **Join Request Code**: A compact, shareable token generated by a new device that wants to join. Contains the requester's public key and label. Can be rendered as a QR code, a URL, or a copyable text string.
- **Inviter (Device A)**: An existing device in the vault's trust group that initiates pairing.
- **Invitee (Device B)**: A new device that wants to join the vault's trust group.
- **Pairing Payload**: The JSON structure encoded within an invite or join-request code.
- **Device_Panel**: The React UI component for device management (desktop + extension).
- **Tauri_Backend**: The Rust backend of the desktop app.
- **Extension_Background**: The background service worker in the browser extension.
- **WASM_Bridge**: zvault-core compiled to WebAssembly for the browser extension.

## Requirements

### Requirement 1: Device Identity Generation (prerequisite)

**User Story:** As a user launching the app for the first time, I want a unique device identity to be automatically generated, so my device can participate in pairing and sync.

#### Acceptance Criteria

1. WHEN a user opens the app with no existing device identity, THE app SHALL prompt the user for a device label and generate a secp256k1 keypair + UUID.
2. THE secret key SHALL be persisted in SecureStorage (OS keyring on desktop, encrypted browser.storage.local in extension).
3. WHEN the identity is generated and the vault has no devices, THE device SHALL bootstrap itself as the first entry.
4. WHEN the identity is generated and the vault already has devices, THE device SHALL NOT auto-admit itself — it must go through the invite or join-request flow.
5. THE app SHALL display the device's own public key in a "My Device" section (copyable, for fallback manual sharing).
6. IF identity generation is invoked when an identity already exists, THE app SHALL show the existing identity instead.

### Requirement 2: Invite Flow — A invites B

**User Story:** As a user with an existing device (A), I want to generate an invite that I can share with my new device (B) so that B can join my vault easily.

#### Acceptance Criteria

1. WHEN the user clicks "Invite Device" on Device A, THE app SHALL generate an Invite Code containing:
   - `type: "invite"`
   - `pubkey`: Device A's Nostr public key (hex)
   - `label`: Device A's label
   - `vault_id`: A unique vault identifier (to prevent cross-vault confusion)
   - `created_at`: Timestamp (for expiry display, not enforced in v1)
2. THE Invite Code SHALL be encoded as a base64url string prefixed with `zvault:` (e.g. `zvault:eyJwdWJ...`).
3. THE app SHALL present the Invite Code in three formats:
   - **QR code** (rendered in-app for scanning by mobile/camera)
   - **Copyable text** (for paste into another desktop app or extension)
   - **Share link** (optional, `https://zvault.app/pair#<code>` — informational only, no server needed)
4. WHEN Device B receives the Invite Code (via scan, paste, or link), THE app on B SHALL:
   - Decode and validate the code
   - Generate Device B's own identity (if not already generated)
   - Display the inviter's info (label, pubkey) for user confirmation
   - On user confirmation: admit Device A into B's device list and generate a Join Response Code containing B's public key
5. THE Join Response Code SHALL be shown on Device B in the same three formats (QR, text, link).
6. WHEN Device A receives B's Join Response Code, THE app on A SHALL:
   - Decode and validate it
   - Display B's info for confirmation
   - On user confirmation: admit Device B into A's device list
7. AFTER both devices have admitted each other, sync SHALL be possible between them.
8. IF the invite code is malformed or undecodable, THE app SHALL show a clear error message.

### Requirement 3: Join-Request Flow — B requests to join A

**User Story:** As a user setting up a new device (B), I want to generate a join request that I can give to my existing device (A), so A can admit me without both devices needing to be co-located.

#### Acceptance Criteria

1. WHEN the user clicks "Request to Join" on Device B (which has no vault or an empty vault), THE app SHALL generate a Join Request Code containing:
   - `type: "join_request"`
   - `pubkey`: Device B's public key (hex)
   - `label`: Device B's label
   - `created_at`: Timestamp
2. THE Join Request Code SHALL be encoded in the same `zvault:` base64url format.
3. THE app SHALL present the Join Request Code in three formats: QR, copyable text, share link.
4. WHEN Device A receives B's Join Request Code (via scan, paste, or link), THE app on A SHALL:
   - Decode and validate the code
   - Display B's info (label, pubkey) for user confirmation
   - On user confirmation: admit Device B into A's device list
   - Generate an Invite Response Code containing A's public key + vault_id for B to complete pairing
5. WHEN Device B receives A's Invite Response Code, THE app on B SHALL:
   - Admit Device A into B's device list
   - Sync can now begin
6. IF the join request code is malformed, THE app SHALL show a clear error message.

### Requirement 4: Code Format and Encoding

**User Story:** As a user, I want pairing codes to be compact and easy to transfer between devices regardless of the method used.

#### Acceptance Criteria

1. ALL pairing codes (invite, join_request, invite_response, join_response) SHALL use the same encoding: `zvault:` + base64url(JSON payload).
2. THE JSON payload SHALL include a `version` field (integer, currently `1`) for forward compatibility.
3. THE JSON payload SHALL include a `type` field to distinguish invite from join_request from response.
4. THE total encoded string SHALL be under 500 characters to fit in QR codes and easy paste.
5. THE QR code SHALL be generated client-side (no network request).
6. THE app SHALL support scanning QR codes via device camera (Android) or pasting text (desktop/extension).
7. Desktop and extension SHALL support paste-based input as the primary method (no camera).

### Requirement 5: Security of Pairing Codes

**User Story:** As a security-conscious user, I want pairing codes to contain only public information, so that intercepting a code does not compromise my vault.

#### Acceptance Criteria

1. Pairing codes SHALL contain ONLY public keys, labels, and non-sensitive metadata. No secret keys, passwords, or vault contents.
2. An attacker who intercepts a pairing code can at most learn the public key and label of a device — this does NOT grant vault access.
3. Pairing SHALL still require explicit user confirmation on BOTH devices (mutual admission).
4. THE vault data is only shared via NIP-44 encrypted sync AFTER both devices have mutually admitted each other.
5. THE app SHALL warn users not to share pairing codes publicly (informational — no enforcement).

### Requirement 6: Device Admission (unchanged core behavior)

**User Story:** As a user, I want the underlying admit/revoke mechanics to remain unchanged so existing sync and CRDT logic continues to work.

#### Acceptance Criteria

1. THE DeviceManager::admit function signature and behavior SHALL remain unchanged.
2. THE OR-Set CRDT merge semantics SHALL remain unchanged.
3. THE vault version counter SHALL increment on every device list mutation.
4. THE VaultFile SHALL be saved atomically after every device list change.
5. Revocation behavior SHALL remain unchanged (permanent in v1, self-revoke prevented).

### Requirement 7: Backward Compatibility

**User Story:** As a user who already has devices paired via the old manual-pubkey method, I want the old method to continue working as a fallback.

#### Acceptance Criteria

1. THE "Admit Device" form (raw pubkey + label paste) SHALL remain available as an "Advanced" option.
2. Devices paired via the old method SHALL continue to work normally.
3. THE new invite/join-request flows SHALL produce the same vault state (DeviceEntry) as the old manual method.

### Requirement 8: UI/UX for Pairing

**User Story:** As a user, I want a clear, guided pairing experience that tells me what to do at each step.

#### Acceptance Criteria

1. THE Device_Panel SHALL have a prominent "Invite Device" button (for the invite flow).
2. THE Device_Panel SHALL have a "Join Existing Vault" or "Request to Join" button (for the join-request flow, visible when no devices exist or as an option).
3. THE Device_Panel SHALL have an "Enter Pairing Code" input area that accepts any `zvault:` code (auto-detects type).
4. WHEN showing a generated code, THE UI SHALL show step-by-step instructions (e.g., "1. Show this QR to your other device, or copy the code below. 2. Wait for the response code from the other device.").
5. THE UI SHALL show a confirmation screen before admitting any device, displaying the device's label and public key (truncated).
6. THE UI SHALL show success feedback when pairing is complete on both sides.
7. THE "My Device" section SHALL always show the current device's pubkey with a copy button.

### Requirement 9: Platform-Specific Behavior

**User Story:** As a user on different platforms, I want the pairing method best suited to my device.

#### Acceptance Criteria

1. **Desktop (Tauri):** Primary methods are copy/paste text code and display QR code for mobile to scan.
2. **Browser extension:** Primary method is copy/paste text code. QR display optional.
3. **Android:** Primary methods are scan QR code (camera) and paste text code.
4. **CLI:** Primary method is print code to stdout / accept code via argument or stdin.
5. ALL platforms SHALL support paste-based input at minimum.

### Requirement 10: Input Validation

**User Story:** As a user, I want pairing codes to be validated before any action is taken, so that invalid codes produce clear feedback.

#### Acceptance Criteria

1. WHEN a code is pasted/scanned, THE app SHALL validate: correct prefix (`zvault:`), valid base64url, valid JSON, required fields present, `version` is supported.
2. WHEN a pubkey in a code is not exactly 64 hex characters, THE app SHALL reject it with a specific error.
3. WHEN a code's `type` does not match the expected type for the current flow step, THE app SHALL show a helpful error (e.g., "This is a join request, but you need to enter an invite response").
4. THE app SHALL NOT crash or panic on malformed input — all decoding is wrapped in error handling.

### Requirement 11: Vault Session Prerequisite

**User Story:** As a user, I want device pairing operations to require an unlocked vault, so that no changes happen without authentication.

#### Acceptance Criteria

1. IF any pairing operation is attempted when the vault is locked, THE app SHALL show an error and prompt to unlock.
2. WHILE the vault is unlocked, all pairing operations SHALL be available.
